# Content Agent and vertical packs

Issue #10 turns verified research into versioned editorial drafts without opening an unconstrained factual side channel.

## Boundary

The Content Agent consumes:
- a workflow in `VERIFIED` or already-`DRAFTED` state;
- the latest `VERIFIED` or human-`REVIEWED` research brief;
- the exact claim/evidence ledger referenced by that research brief;
- a versioned `VerticalPack`;
- a requested locale and content format supported by that pack;
- a provider-agnostic `ContentAdapter`.

It produces:
- headline;
- deck;
- structured content sections;
- rendered body;
- SEO metadata;
- deterministic source citations;
- structured internal-link suggestions;
- explicit unsupported factual assertions;
- versioned draft provenance.

The Content Agent does not browse or fetch arbitrary sources.

## Vertical pack contract

A vertical pack is identified by `key + version` and configures:
- audience;
- supported locales;
- default locale;
- supported formats;
- default format;
- tone/style notes;
- prohibited phrases;
- headline/deck constraints;
- minimum section count;
- source/citation rules;
- SEO constraints;
- internal-link topics.

The workflow vertical key/version must match the selected pack exactly.

The draft persists the full pack snapshot so historical output remains reproducible even if a later pack version changes.

## Built-in validation packs

### Generic demo

`generic-demo@1`
- English only;
- article/brief;
- neutral explanatory voice;
- generic source/citation rules.

### Trigenys Insight pilot

`trigenys-insight@1`
- French and English;
- article/brief/analysis;
- professional, direct, lively and locally grounded voice;
- explicit anti-filler/prohibited phrasing rules;
- Cameroon/Africa-oriented audience context;
- citation-first source rules.

The two packs exercise the same Content Agent core without vertical-name branches.

## Claim safety

The model adapter receives only the supplied claim ledger and its evidence references.

Every generated section must enumerate its factual assertions. Each assertion carries:
- a canonical `claim_key`, or
- `null` / an unknown key when the assertion is not in the ledger.

The service independently resolves those keys:
- known key → linked to the canonical claim;
- unknown/null key → persisted in `unsupported_factual_claims`.

The model cannot promote an unknown claim into supported state.

Citation records are generated by Editorial OS from the canonical claim↔evidence ledger, not invented by the model.

## Draft provenance

A draft records:
- research brief ID;
- editorial brief ID;
- vertical pack key/version and full snapshot;
- locale/format;
- structured sections;
- SEO metadata;
- citations;
- internal-link suggestions;
- unsupported factual assertions;
- exact draft↔claim links;
- adapter identity;
- stable input fingerprint.

The first persisted draft transitions `VERIFIED → DRAFTED`. Additional supported locales or formats may be generated from the same verified research while the workflow remains `DRAFTED`.

## Revisions

Operator feedback creates a new draft version.

A revision:
- points to `revision_of_id`;
- reuses the exact research brief;
- reuses the exact editorial brief;
- reuses the persisted vertical-pack snapshot;
- rebuilds claim links/citations from the canonical ledger;
- persists the operator feedback;
- never mutates the prior draft.

Repeated identical revision requests reuse the persisted result through the input fingerprint.

## Style validation

Before persistence, deterministic validation checks:
- locale/format support;
- headline maximum length;
- deck maximum length;
- minimum section count;
- SEO title/description limits;
- required SEO keywords;
- prohibited phrases.

A style violation fails closed and leaves workflow state unchanged.
