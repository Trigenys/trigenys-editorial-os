# Engineering contract

This repository was generated by Trigenys AppFactory and follows the Trigenys RAIDER Engineering Standard.

## Working rules

- Keep domain logic separate from provider adapters and transport code.
- Prefer explicit contracts, state machines and small boundaries over multipurpose agents.
- Every remote mutation must be retry-safe or explicitly documented otherwise.
- Every consequential agent decision must retain evidence: inputs, sources, model/provider, prompt/version, output, confidence and timestamps as appropriate.
- Human gates are policy, not UI-only behavior. They must be enforced by the workflow engine.
- Never log secrets or raw credentials.
- Add dependencies only when Adopt/Adapt is better than rebuilding.
- Every issue must contain a verifiable Proof of Done.
- Do not report work complete until relevant tests, typechecks/builds and acceptance evidence pass.
- Record significant failures and near misses in `docs/engineering/lessons-learned.md`.

## RAIDER

For material changes, verify:

- **Reusable** — capabilities can serve more than one vertical/consumer without forks.
- **Agnostic** — provider, repository, model, CMS and channel specifics live behind configuration/adapters.
- **Idempotent** — re-running the same desired operation converges without duplicates.
- **Durable / Non-regressive** — supported behavior stays green; public contracts are versioned.
- **Engineering-grade** — security, testing, observability, explicit contracts and reuse-first reconnaissance are part of design.
- **Retroactive** — existing verticals/data can adopt changes without destructive reset.

Failure memory and reuse-first ecosystem reconnaissance are mandatory supporting practices.

## Product invariants

1. A source claim must remain traceable to its evidence.
2. A low-confidence or policy-sensitive item cannot bypass the configured human gate.
3. Publishing is a separate state transition from drafting.
4. Agents propose; the orchestrator owns workflow state.
5. Vertical packs configure editorial behavior; they must not fork the core.
6. Provider outages or retries must not create duplicate articles, assets or social posts.
